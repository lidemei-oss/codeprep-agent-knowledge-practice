# CodePrep-Agent 简历面试问答：按当前代码核对版

核对日期：2026-10-15。适用范围：截图中的 CodePrep-Agent 项目经历，以及当前 knowledge-practice 项目代码。本文包含 60 道问题、参考回答和常见追问。

回答中的“当前实现”来自代码；“进一步改进”属于设计建议，不能说成已经完成。第一人称回答是练习模板，个人承担范围必须按本人实际参与情况调整。本文不修改项目代码，也不重新执行模型评测。

建议复习顺序：先讲通 01、04、06，再练 08～15 的异步一致性；随后练 21～32 的 RAG；最后练 37～55 的数据库、Redis 和权限通信。每题先说结论，再说一个实现依据，最后回答失败时怎么处理。

## 第一组：项目开场与整体架构

### 01｜请用 2～3 分钟介绍项目。

参考回答：CodePrep-Agent 面向 Java 学习和面试准备，用户上传自己的学习资料后，可以进行带来源的问答、按文档分组刷题、答案评测和错题复练。后台采用 Spring Boot、MyBatis-Plus 和 MySQL 管理业务数据，Elasticsearch 负责关键词和向量检索，Redis 保存短期对话上下文，RabbitMQ 承担异步文档处理。

上传时先保存文件，在同一个 MySQL 事务中写入 PROCESSING 文档记录和 Outbox 任务，然后返回。发布器把任务可靠地发送到 RabbitMQ；消费者领取处理资格后解析文档、按结构切块，调用 Qwen 生成向量，保存切片并建立 ES 索引，完成后把文档发布为 READY。

问答时先限制组织标签、类别等范围，再做 BM25 与 KNN 混合召回。现在增加了证据审核，只有片段确实支持问题，才交给 DeepSeek 生成回答。证据不足会尝试改写重检和公开搜索，服务故障则单独处理。

我重点准备的工程问题是异步任务可靠投递、重复消费和模型调用的事务边界：用 Outbox 记录发送意图，用 MySQL 条件更新和租约控制文档处理资格，用两个短事务把答题占用和结果保存包住，把模型等待放在事务外。

常见追问：上述哪些部分由你实现？请按实际贡献回答，不要把“项目包含该能力”直接等同于“完全由我独立开发”。

### 02｜这个项目解决什么问题，为什么不直接问大模型？

参考回答：直接提问主要依赖模型已有知识，未必符合用户上传资料的版本、范围和表述。项目把指定学习资料作为题源和回答依据，提供文档引用，并把学习过程延伸到出题、评测和复练。它的价值包括限定资料范围、记录学习状态、把检索证据展示给用户核对。

常见追问：RAG 能保证答案一定正确吗？不能。解析、切块、召回、证据判断、生成都可能出错。引用让问题更容易追溯，证据审核降低无依据生成的机会，但效果还要通过有标注样本验证。

### 03｜Controller、Service、Mapper 如何分工？接口之间怎么调用？

参考回答：Controller 接收 HTTP 请求，读取登录身份，校验参数和权限，把业务操作交给 Service。Service 负责状态流转、事务边界和对模型、MQ、ES 等组件的调用。Mapper 负责 MySQL SQL。数据通过实体和响应对象逐层返回。

例如上传是 Controller → 上传服务 → 文档受理服务 → 文档 Mapper 与 Outbox Mapper；Agent 出题是编排服务直接调用刷题服务，不是后端再通过 HTTP 请求自己的刷题 Controller。这样模块可以复用业务能力，避免把 HTTP 层当成内部业务接口。

常见追问：为什么不在 Controller 直接调 Mapper？简单读操作技术上可以，但本项目上传、评测都涉及多步状态与一致性规则，放在业务层更容易统一事务、复用和测试。

### 04｜请分别说出入库、问答、评测三条链路。

参考回答：

```text
入库：文件落盘 → 文档与 Outbox 同事务保存 → HTTP 返回 PROCESSING
      → 发布器投递 RabbitMQ → 消费者领取资格 → 解析 → 切块
      → Qwen 向量化 → MySQL 切片／ES 索引 → 发布 READY → 消费 ACK

问答：身份与范围校验 → 读取会话历史 → BM25＋KNN → 融合候选
      → 证据审核 → 必要时改写、重检或公开搜索
      → 组织 Prompt → DeepSeek → 流式返回 → 完成后保存上下文

评测：提交 requestId 与答案 → 短事务登记 pending
      → 事务外评测和生成下一题 → 短事务保存成绩、结果与幂等记录
      → 返回结果；完成后的重复请求重放原结果
```

常见追问：上传接口成功表示可以问答吗？仅表示文件及任务已受理；READY 才表示完成当前处理链路。流式返回开始前，检索和证据审核仍需要时间。

### 05｜你遇到过什么有价值的问题，如何定位？

参考回答：可以选“库外问题也有召回结果”。我用自建资料做检索评测，发现 8 个库外问题都拿到了 8 个候选，说明非空列表不能代表证据充分。我把原始召回和最终证据选择分开，增加结构化证据审核、片段 ID 校验和故障分支，并让普通问答与 Agent 复用同一套流程。

常见追问：改完准确率提高多少？完整的新质量复测尚未完成，真实模型调用出现超时和 503，因此只能说流程已实现并通过回归测试，不能报未经测量的提升百分比。另一个可讲案例是数据库已提交而 MQ 发送失败，通过 Outbox 恢复发送。

## 第二组：PDF 上传、RabbitMQ 与 Outbox

### 06｜上传一份 PDF 后，哪些同步做，哪些异步做？

参考回答：同步阶段校验权限和文件非空，生成文档 ID，把文件保存到上传目录；随后进入 MySQL 本地事务，同时插入文档记录与 Outbox 任务。事务提交后接口返回文档 ID、PROCESSING 状态和初始切片数，不等待向量化，也不等待 MQ 消费完成。

异步阶段由定时发布器投递 documentId。消费者通过 documentId 找到原文件，领取处理资格，再做 Tika 解析、结构切块、Qwen 向量化、MySQL 切片保存和 ES 索引。文件没有通过 MQ 传输，消息只是任务标识。

常见追问：文件保存成功，数据库事务失败怎么办？文件系统不参与 MySQL 事务，当前可能留下孤立文件。进一步改进是失败时清理本次文件，或定时对账清理没有文档记录的过期文件；不能说事务会自动回滚磁盘文件。

### 07｜为什么用 RabbitMQ，不直接开线程？为什么选它而不是 Kafka？

参考回答：解析和向量化耗时较长，放在上传请求内会增加请求超时风险。RabbitMQ 将受理和处理解耦，通过队列缓冲任务，并提供消费确认、重投递和死信机制。普通线程池任务主要留在当前进程，进程退出后不能仅凭线程池恢复。

本项目是文档后台任务处理，不依赖大规模事件日志回放。RabbitMQ 的路由、确认与失败队列适合这个需求。Kafka 也能实现任务处理，但它的分区日志、消费位点和回放模型需要不同的设计，不能因为“面试常问”就作为唯一选型依据。

常见追问：有 MQ 就不会丢任务了吗？不是。业务数据库到 MQ 之间仍有失败窗口，需要 Outbox；消费产生的业务副作用仍要幂等和补偿。

### 08｜Outbox 到底有什么用？

参考回答：Outbox 是 MySQL 中的待发送任务表。文档受理和发送意图在同一个事务中提交，避免文档已经入库、应用却没有留下任何发送任务就退出。发布器扫描待发送记录，发送失败保留任务并重试，收到确认再标记 SENT。

```text
本地事务：INSERT cp_document + INSERT cp_document_outbox
事务提交：文档记录与发送意图一起可见
后台投递：PENDING → SENDING → SENT
失败路径：SENDING → PENDING，设置下一次尝试时间
```

常见追问：Outbox 是分布式事务吗？当前用的是本地事务加异步重试，实现最终一致性的基础。它不把 MySQL 和 RabbitMQ 变成一个原子提交，也不能无条件保证永久故障下最终成功。

### 09｜发布确认和消费确认有什么区别？mandatory 有什么作用？

参考回答：发布确认是 Broker 对生产者发送的确认；消费确认是消费者处理后给 Broker 的确认。前者不代表向量化成功，后者也不会自动更新 MySQL 的 Outbox。两条确认链路互相独立。[RabbitMQ 官方确认机制说明](https://www.rabbitmq.com/docs/confirms)

当前启用 correlated publisher confirm、publisher returns 和 mandatory。发布器等待最多 10 秒，只有 confirm 为 ACK 且没有 returned message，才尝试把任务改为 SENT。mandatory 让无法路由到队列的消息返回生产者；不能只看到 ACK 就忽略路由失败。

常见追问：确认超时说明发送失败了吗？只能说明结果不确定，消息可能已入队。因此会重试，并要求消费端能够处理重复任务。

### 10｜Broker 已确认，但 Outbox 还没标记 SENT 就宕机，怎么办？

参考回答：重启后 SENDING 的发布租约到期，发布器可以重新领取并再次发送，因此允许重复投递。当前 Outbox 以 document_id 为主键，一个文档维护一条任务记录；发布 token 防止旧发布器错误回写新一轮状态。

消费端先识别已 READY 文档并直接 ACK；对于 PROCESSING 文档，必须先通过数据库条件更新领取资格，不能单靠一次状态查询决定执行。切片 ID 使用 documentId 与 chunkNo 构成，ES 使用同一 ID 写入，配合领取和重建流程控制重复数据。

常见追问：这叫 exactly-once 吗？不应这样宣传。消息可能重复，模型调用也可能重复；项目依赖至少一次投递场景下的业务幂等与恢复措施。

### 11｜两个消费者同时看到 PROCESSING，怎样只让一个开始清理重建？

参考回答：把判断和更新合成一条 MySQL 条件 UPDATE，并依据受影响行数判断。只有更新成功的消费者可以进入清理和向量化。

```sql
UPDATE cp_document
SET ingest_owner = :token,
    ingest_lease_until = :leaseUntil
WHERE id = :documentId
  AND status = 'PROCESSING'
  AND (ingest_owner IS NULL OR ingest_lease_until <= :now);
```

受影响行数为 1 表示领取成功，为 0 表示当前不符合领取条件。不能用先 SELECT 再无条件 UPDATE，因为两次操作之间存在竞争窗口。当前未领取到的重复投递会 ACK 并退出，不进入清理。

常见追问：用了 synchronized 是否就够了？不够，它只协调同一个 JVM 的相关对象。跨实例争抢依靠 MySQL 条件更新。

### 12｜消费者领取成功就宕机，是否永远占着锁？

参考回答：当前持有的是数据库中记录的逻辑处理资格，不是覆盖整个向量化过程的长期行锁。文档租约是 30 分钟，处理过程中每 30 秒尝试续租。宕机后续租停止，租约到期允许重新领取。

对账任务默认每 60 秒检查一次。对于 PROCESSING、存在已过期消费租约且 Outbox 为 SENT 的文档，会把 Outbox 重新置为 PENDING，由发布器再次投递。发布器自己的租约默认 30 秒，和文档消费租约是两套不同机制。

常见追问：恢复是不是立即发生？不是，需要等待租约到期和定时扫描；配置体现恢复速度和误接管风险的权衡。当前心跳不能识别所有“线程活着但业务永久卡住”的情况，还需要阶段超时和进度监控。

### 13｜租约、token 是否彻底解决旧消费者恢复后的并发写问题？

参考回答：当前会在清理前、每次向量化后的写入前，以及结束时核验 owner 和租约；最终 READY／FAILED 更新也带 token 条件，避免旧 owner 随意完成文档。

但核验 MySQL 和写 ES 是分开的操作。如果旧线程在核验通过后长时间暂停，租约过期被接管后又恢复，仍有跨系统的检查与使用时间窗口。当前没有 ES 侧的严格 fencing 或版本隔离，不能说已经彻底解决所有暂停恢复竞争。

常见追问：怎么完善？可引入 ingestionVersion，每轮使用独立版本的切片 ID、只清理本版本数据，成功后用带 owner/version 条件的短事务切换 activeVersion；查询只接受活动版本。ES 写入还需配合版本约束或隔离，不能只多加一次 owner 查询。

### 14｜只写入一部分切片就崩溃，如何恢复？会不会查到半成品？

参考回答：当前重试前需要先取得处理资格，然后清理该文档的 MySQL 切片和 ES 数据，再从源文件重建。切片 ID 为 documentId-chunkNo；MySQL 主键阻止同 ID 重复插入，ES 同 ID PUT 有覆盖语义，不能把二者都说成自动 upsert。

ES 每条切片先写 PROCESSING，正常完成后统一改 READY；查询带 READY 过滤，降低处理中的片段被检索到的风险。之后 MySQL 文档才改 READY，并发送消费 ACK。

常见追问：ES 和 MySQL 的 READY 是原子切换吗？不是。ES 发布在前，MySQL 更新在后，存在跨系统窗口；当前也没有完整校验 update-by-query 响应中的所有部分失败。不能宣称生产级原子发布，版本化发布与对账是进一步改进。

### 15｜消费失败怎样重试？死信是不是自动重试？

参考回答：当前消费者在同一次监听调用中最多立即尝试 3 次。仍失败时尝试把自己拥有的文档标为 FAILED，再执行 basicNack(deliveryTag, false, false)，交给已配置的死信交换机与死信队列。这个实现是本地循环重试，不是延迟队列退避重试。

发布失败是另一套策略：Outbox 默认从 1 秒起指数退避，最大间隔 5 分钟，并保存次数和最近错误。消费者处理重试和发布器发送重试不能混为一谈。

常见追问：死信进入队列后自动恢复了吗？当前没有通用的自动死信修复、重放流程。需要先定位原文件、模型或 ES 故障，修复后受控重置状态并重新投递。永久解析失败不应无限重试。[RabbitMQ 对 nack 与死信的说明](https://www.rabbitmq.com/docs/confirms)

### 16｜交换机、队列、持久化、prefetch 在项目中怎么配置？

参考回答：当前是持久化 DirectExchange，按 routing key 精确绑定文档任务队列，主队列绑定死信交换机，另有持久化死信队列。监听器使用手动 ACK，prefetch 为 2，消费者并发范围配置为 1～2。

prefetch 限制单个消费者未确认消息的数量，控制其占用的处理中任务。向量化依赖本地模型算力或远端接口额度，增加并发并不一定更快，可能增加超时和内存占用。

常见追问：durable 是否就绝对不丢？不能。还需要消息持久性、发布确认、存储与部署可靠性。Compose 里是本地单节点 RabbitMQ，不是已经验证过容灾的集群；当前代码没有声明 quorum queue。

### 17｜分片上传如何标识、检查齐全和合并？断点续传到什么程度？

参考回答：先创建 uploadId，并记录文件名、分片总数、总大小、用户、类别、组织和分组。客户端用 uploadId 与分片序号上传；后端验证序号范围和单片大小，将分片写成文件并记录已收序号。完成时检查数量，按 0 到 totalChunks-1 合并，并核对合并后的字节数，再进入普通文档受理流程。

当前单片最多 5 MiB，总大小上限是 500,000,000 字节；上传状态保存在进程内 ConcurrentHashMap。示例前端按钮使用整文件 multipart 上传，分片接口能力在后端。

常见追问：重启后继续传、文件秒传、SHA-256 校验做了吗？未完整实现。没有持久化上传状态、完整缺片查询和内容哈希验证，也没有覆盖所有并发合并问题。简历写“分片上传”准确，写“完整跨重启断点续传”会超出当前实现。

### 18｜Tika 解析之后怎么按结构切块？为什么是 700／160／80？

参考回答：Markdown 优先按 UTF-8 读取；PDF、DOCX 等通过 Tika 提取文本。切块器识别 Markdown 标题、中文章节、编号标题、段落、列表和围栏代码块，在同章节内拼接；超长内容优先按段落、换行和标点递归拆分，最后才按字符边界兜底。

默认最大估算 700 Token、短尾块合并参考值 160、重叠预算 80。重叠在同章节内、预算允许时保留，代码块附近有特别处理，并不是每块都固定重叠 80。片段带文档名和识别出的章节路径。参数是当前工程取值，尚未证明是效果最优配置。

常见追问：是精确 tokenizer 和 embedding 语义聚类吗？不是。Token 是本地估算，短块按章节与长度合并，没有用 embedding 做语义聚类。Tika 输出纯文本，PDF 的跨页段落、复杂表格和章节识别取决于提取质量；当前没有可靠页码坐标和完整 OCR 流程。

### 19｜用户上传后立即提问，如何区分未就绪和没有答案？

参考回答：文档列表返回 PROCESSING、READY、FAILED，前端对处理中资料定期刷新。ES 检索和 MySQL 题源查询过滤 READY；分组刷题没有 READY 资料时直接提示等待处理。

当前通用问答请求主要携带组织和类别，没有强制绑定某一份上传文档，也没有完整的“先查指定文档状态再问答”流程。因此“这份资料还在处理中”不能由所有通用问答自动准确识别；证据不足还可能按设置回退公开搜索。

常见追问：怎么完善？让问题绑定 documentId 或明确文档范围，先验证权限与处理状态；指定资料未 READY 时返回处理中，不把它当成资料里没有答案。公开搜索应明确展示来源，不能冒充刚上传文件的解释。

### 20｜文档一直 PROCESSING／chunks 0，或者处理特别慢，怎么排查？

参考回答：按 documentId 查文件是否存在、文档状态、Outbox 的 status/attempt_count/last_error，再看队列 ready/unacked、消费日志和租约。随后分阶段看 Tika、切块数量、单次 embedding 时延、ES 写入与发布是否卡住。页面 chunks 0 不能直接证明切分没有执行，因为文档切片总数在成功完成时更新。

当前每片同步向量化，并逐条调用 ES 写入且 refresh=wait_for，文档越长等待次数越多。这是明确的优化候选：分阶段计时后，再考虑模型支持的批量 embedding、ES Bulk、减少逐片刷新和有界并发。

常见追问：这些优化已经上线了吗？当前没有全部落地。也不能凭一个页面卡片判断是 Kafka、MQ 或网络问题，必须沿链路查证。解析端还要核对文本提取长度限制和长 PDF 是否截断。

## 第三组：RAG、Elasticsearch 与证据判断

### 21｜Qwen、Elasticsearch、DeepSeek 各做什么？2048 维怎么来的？

参考回答：Qwen Embedding 把文档片段和问题转换为向量；ES 保存可检索字段与向量，执行关键词和近邻召回；DeepSeek 用于任务路由、改写、证据审核、回答生成和评测等语言任务。向量化不等于生成答案。

当前 ES dense_vector 的 dims 固定为 2048，embedding 客户端也检查维度。对配置名包含 Qwen3-Embedding-4B 且返回维度更大的情况，代码截取前 2048 维并做 L2 归一化。这个策略不能直接套用到任意 embedding 模型；换模型要核对模型能力并实测。

常见追问：不同模型都输出 2048 维就能混用吗？不能。维度相同不代表同一个语义空间。更换模型或关键预处理通常要重建文档向量，并保证问题使用同一配置。

### 22｜为什么同时用 BM25 和向量检索？各举一个例子。

参考回答：BM25 擅长精确术语，如“CallerRunsPolicy”“SELECT FOR UPDATE”“HashMap treeify”。向量检索擅长表达不同但语义接近的问题，如“很多请求同时查一个刚失效的热点数据，怎么防止把数据库打满”，可以找到“缓存击穿、互斥重建”相关资料。

两路结合是为了覆盖不同表达方式，不代表融合后每一道题都更好。参数名、缩写和代码符号容易需要关键词精确匹配，口语化和同义表达更需要语义召回。

常见追问：BM25 是否就是关键词出现次数？它还考虑词的区分度、词频饱和和文档长度归一化。向量相似度也不是事实正确率，仍需要后续证据审核。

### 23｜两路检索是一个请求还是两个？各取多少条？

参考回答：当前业务代码先调用关键词查询，再调用 KNN 查询，是两个独立且顺序执行的 ES 请求，然后在 Java 中按 chunkId 合并。这样容易分别记录命中数、排名和诊断单路效果，但增加了往返与串行等待。

默认 BM25 请求 size=40；KNN 的 k=8、num_candidates=40，同时请求 size=40，不能因此说 KNN 最终返回了 40 个近邻；k 仍限制近邻结果规模。融合候选最多取 8 条，再由新增证据审核选取最终使用的片段。

常见追问：为什么不并行或用 ES 内置融合？这是可优化方向，可以比较并发请求、_msearch 或适用版本的检索组合能力；当前没有声称它们已经实现。模型失败生成不了问题向量时，现有逻辑可继续尝试关键词检索。

### 24｜IK 用的是 ik_max_word 还是 ik_smart？查询范围怎么限制？

参考回答：当前自定义 ik_text analyzer 使用 ik_max_word tokenizer，title/content 用 ik_text，keywords 字段也配置 ik_max_word。没有单独设置 search_analyzer，因此不能回答“入库用 max_word、查询用 smart”。

查询通过 filter 限制 orgTag、category、READY 状态；指定刷题分组时，先从 MySQL 得到该组 READY 文档 ID 集合，再用 terms 限制 documentId。过滤条件不参与相关性得分，权限也不会只靠 Prompt 告诉模型遵守。

常见追问：为什么采用细粒度分词？希望覆盖更多中文组合，但会增加索引词项及噪声；是否改为更粗粒度查询分词要对照评测。keywords 字段虽在 mapping/query 中，但当前入库没有显式填充它，不能说已做自动关键词抽取。

### 25｜RRF 公式是什么？为什么不直接相加 BM25 和向量得分？

参考回答：标准 RRF 按排名融合，对文档 d 的分数为：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

只对命中的召回列表累加，rank 从 1 开始；当前采用的平滑常数为 60。它避免直接混合两套量纲和分布不同的原始分数，让同时在多路靠前的候选获得支持。BM25 可能得到十几分，向量检索的分数则是另一种范围，直接相加容易由量纲决定排名。

常见追问：加权分数融合一定不行吗？不是。经过归一化、校准和真实评测，也可以加权融合。RRF 的优点是对原始分值尺度依赖较少，不保证所有问题都改善。

### 26｜你代码是不是纯 RRF？为什么联合索引那题融合后反而下降？

参考回答：当前不是纯 RRF。每路先加 1/(60+rank)，还叠加了分数补偿：向量分数取非负后乘 0.05；关键词分数除以 10 后截到 [0,1]，再乘 0.2。这些是已有启发式权重，没有通过学习得到。

因此简历更严谨的说法是“基于 RRF 的融合排序”，不能说完全忽略原始分数。本次真实样本里，一个联合索引问题在 KNN 排第一、混合后排第二，纯 RRF 对照也排第二，说明不能只怪分数补偿。

常见追问：怎么改？本轮已加问答证据筛选和选择后排序；纯 RRF、权重调整及更专门的 reranker 仍应通过固定测试集比较，不能宣称新增审核已证明全量质量提升。

### 27｜如何解决“召回非空就回答”？

参考回答：把召回候选与最终证据分开。BM25/KNN 的结果先交给证据审核，判断正文是否支持问题要求的实体、条件和机制，再返回 SUPPORTED、INSUFFICIENT 或 ERROR。只有 SUPPORTED 且 Java 校验通过，才把选中片段交给回答模型。

例如问“CallerRunsPolicy 为什么能减缓提交速度”，候选只列举四种拒绝策略，并不足以解释因果关系。即使召回 8 条，也可以全部判定不足；如果有一条解释了调用者线程执行任务占用提交时间，就可以只选这一条。

常见追问：代码为什么还判断 citations.isEmpty？因为现在这个列表是审核后的证据列表，原始候选保存在诊断记录中。错误或不足的审核不能把原始列表直接透传去生成。

### 28｜证据审核输入、输出和防乱选措施是什么？

参考回答：输入为原问题、最多六条历史和候选的 ID、标题、正文。历史仅用于指代消解，不作为事实证据。模型以 JSON 返回状态和 selectedChunkIds，后端从原候选取回正文；普通问题建议 1～3 条，默认硬上限 5 条。

后端检查 JSON 结构、状态和列表是否一致、ID 是否属于候选、是否重复、是否超数量及上下文预算。候选正文默认最多 20,000 字符，选用证据的上下文预算为 12,000 字符；单次审核默认 30 秒超时。异常时返回 ERROR，不把模型自写文字当成原文。

常见追问：低温度或合法 JSON 能保证语义正确吗？不能。结构校验只能约束格式和引用来源，审核模型仍可能误判；还需有答案／无答案样本、跨片段问题、人工复核和延迟成本评测。新审核目前覆盖知识问答与 Agent 问答，并非已经替换所有刷题路径。

### 29｜问题改写怎么做，何时公开搜索？会不会改偏？

参考回答：仅在证据不足时尝试一次改写。启用模型时要求保留原问题实体、条件和意图，输出单行技术检索查询，不添加事实；关闭模型时用简单规则删除部分口语词。改写结果为空、相同或调用失败时，不做无意义的同查询重试。

改写后的候选仍针对原始问题进行审核，减少“搜索问题已经变了”的风险。仍不足且允许联网时，再使用 Tavily 搜索原问题，并对公开候选执行同样的证据审核。公开结果也可能没有答案。

常见追问：改写现在会带最近六条历史吗？当前改写调用主要接收问题文本，新增的六条历史用于证据审核和最终 Prompt。不能把所有阶段都说成已实现上下文查询重写。

### 30｜零召回、证据不足、检索故障如何区分？

参考回答：零召回是查询正常完成但没有候选；证据不足也可能有候选，只是不能支持问题。二者允许进入改写和必要时公开搜索。ES 异常先尝试 MySQL 切片的简单关键词降级，并保留 privateIndexUnavailable 标记。

若降级候选有充分证据，可以继续回答；若降级也没有支持，按私有检索故障停止，不能伪装成“资料没有答案”。审核模型超时、503、格式不合法则是审核故障，同样停止生成。公开搜索异常单独返回公开搜索不可用。

常见追问：MySQL 降级是 FULLTEXT 吗？不是。当前先取可用切片，再在 Java 中做简单文本匹配与排序，只是小规模兜底能力，不能当作等价的 BM25 或高吞吐检索引擎。

### 31｜带引用回答怎么实现？能定位 PDF 第几页吗？

参考回答：每个选中片段都有 chunkId、documentId、标题、chunkNo、正文等信息，公开来源还带 URL。构造 Prompt 时为证据编号 [1]、[2]，要求模型在回答中使用对应编号，响应同时返回引用对象。

Agent 问答会检查是否存在引用标记、编号是否越界，不符合时标记 REVIEW_REQUIRED；这个检查并不是逐句验证答案与证据的语义一致。普通流式问答共用生成前的证据审核，但没有完全相同的生成后引用校验流程。

常见追问：能否定位原文页码？当前主要定位到文档和切片，章节路径嵌在片段正文中，没有可靠的 pageStart/pageEnd 或 PDF 坐标字段。不能把 chunkNo 当页码。如果需要高亮原文，要在解析阶段保留页码和字符位置，再贯穿切分、存储与引用。

### 32｜怎么测 RAG 召回效果？为什么 Recall 高仍可能不好？

参考回答：先准备固定资料和测试问题，人工标注每题应命中的证据 ID，并加入库外问题。用同样语料分别跑 BM25、KNN 和混合检索，统计 Recall@K、Precision@K、Hit@K、MRR，再评估证据选择、回答正确性、引用支持度和耗时。

```text
Recall@K = TopK 中相关切片数 / 标注的全部相关切片数
Precision@K = TopK 中相关切片数 / 返回切片数
Hit@K = 是否至少有一条相关证据进入 TopK，再对问题求平均
MRR = 第一条相关结果排名倒数的平均值；未命中计 0
```

跨片段问题仅 Hit 高还不够，需要看必要证据覆盖率。库外问题单独看错误放行、正确拒答与服务故障；不能把超时当成正确拒答。Recall 高但固定返回大量无关切片，会增加上下文噪声。所有指标都要交代标注口径与分母。

## 第四组：受控 Agent 与错题复练

### 33｜Agent 和普通 RAG 有什么区别？分模块了还叫 Agent 吗？

参考回答：RAG 是知识获取与生成的一条能力链，Agent 在其外层根据任务选择业务能力并观察结果。用户说“解释缓存击穿”，进入知识问答；说“用这组资料给我出题”，进入刷题；提交答案进入评测；带上已有练习会话可进入复盘与针对性训练。

模块是能力的组织方式，编排服务负责把这些能力组合起来。当前适合称为“受控 Agent 工作流”：动作有限、服务调用显式、步骤可追踪，不是模型自主写代码或任意调用网络工具的通用 Agent。

常见追问：是否使用 Spring AI、LangChain4j？当前没有，以 Spring 服务、模型 HTTP 调用和显式编排实现。用了某个框架不自动等于 Agent，没有框架也可以有受控的任务选择与执行流程。

### 34｜规划器使用规则、模型还是两者结合？

参考回答：两者结合。请求含 questionId、answer 或 requestId 等答题字段时，优先路由评测，再由编排器检查参数是否完整；含 practiceSessionId 且不触发答题分支时进入错题复盘。普通自然语言任务交给模型建议“知识检索”或“开始刷题”；调用失败后用刷题、练习、quiz 等关键词规则兜底。

动作定义在枚举中，编排器用 switch 调用对应服务。身份、会话归属、组织标签和评测参数都由后端校验，不能让模型决定用户有没有权限。

常见追问：工具白名单是否无漏洞？当前限制在有限枚举，但模型建议的允许值校验仍可更严格：Prompt 只要求两个动作，代码对其他枚举动作的限制并不完全等于两个值白名单。可以如实说“受控有限路由”，不要宣传成已完成严格形式化工具授权。

### 35｜Agent 的工具有哪些？如何停止，如何排查？

参考回答：业务动作有知识问答、创建练习、答案评测和错题复盘。问答内部再使用私有检索、改写、公开搜索、证据审核与生成等能力。执行结果记录步骤、观察结果和证据信息，保存在 MySQL 的 Agent 运行记录中。

停止条件包括证据不足且可用路径已经耗尽、检索或审核故障、参数权限不满足。代码还限制最多记录 8 个步骤，避免流程无界增长。它是固定分支与有限重试，并不是通用的自主规划循环。

常见追问：8 步是否保证不超时、不超预算？不能。部分调用有超时，但步骤数不等于模型调用总时长或 Token 预算；还需要端到端截止时间、取消传播和成本统计。当前轨迹是业务动作摘要，不是模型隐藏推理过程。

### 36｜项目里的 Skill 实际做什么？

参考回答：当前有错题复盘 Skill。先读取本人刷题记录，汇总 missingConcepts 出现频次，取最多三个薄弱点；没有明确缺失概念时，可从低分题提取复习方向。随后在原组织、类别和原文档分组内检索相关资料，生成简短复盘，并创建三题针对性练习。

它是可复用的业务流程封装，不是动态安装的技能市场，也不是读取任意 SKILL.md 执行指令。无历史、无薄弱点和无资料时会返回对应结果。

常见追问：错题复盘是否也经过新增的证据充分性审核？当前仍使用自己的检索和引用处理，尚未全部接入问答的新版审核链路。可以作为后续统一策略的方向，不能把问答改动宣传成所有模块都已升级。

## 第五组：MySQL、MyBatis-Plus、事务与并发

### 37｜数据库有哪些表？分别存什么？

参考回答：当前有六张核心表，职责如下。

| 表 | 核心字段 | 用途 |
|---|---|---|
| cp_account | username、password_hash、roles_json、org_tags_json | 用户、密码摘要与权限信息 |
| cp_document | id、title、category、org_tag、status、file_name、created_at、chunk_count、group_name、ingest_owner、ingest_lease_until | 文档元数据、分组与处理资格 |
| cp_chunk | id、document_id、title、content、category、org_tag、chunk_no | 切片正文与文档关联 |
| cp_document_outbox | document_id、status、attempt_count、next_attempt_at、lease_until、claim_token、last_error、created_at、updated_at、sent_at | 可靠发送任务 |
| cp_practice_session | id、username、state_json | 当前题、评测、成绩、历史及提交状态快照 |
| cp_agent_run | id、username、result_json | Agent 运行结果、轨迹及相关证据 |

原文件在上传目录，向量在 ES；MySQL cp_chunk 没有 embedding 字段。分组目前是文档的 group_name 字段，没有独立 cp_group 表。schema 中也没有建立完整的外键约束体系，关联一致性主要由业务代码维护。

常见追问：为什么 state_json 存一大段？便于保存和恢复小型会话状态，但不利于按题统计、唯一约束和持续增长后的写入效率。进一步可拆分题目、提交、评测和复习记录表。

### 38｜MyBatis-Plus 怎么配置？增删改查怎么执行？

参考回答：使用 Spring Boot 3 对应的 MyBatis-Plus starter，配置 MySQL datasource；启动类通过 MapperScan 扫描 Mapper 包，开启下划线到驼峰映射。Mapper 继承 BaseMapper，通过实体映射表，使用 insert、selectById、updateById、delete 等通用方法。

例如上传插入文档，列表用查询后组装响应，移动分组更新 group_name，重建前根据 document_id 删除旧切片。条件查询使用 QueryWrapper；任务领取和 SELECT FOR UPDATE 等关键 SQL 通过 Mapper 注解显式实现。当前启动时执行 schema.sql，另有文档租约字段迁移逻辑，不是数据库全靠 ORM 自动推导生成。

常见追问：MyBatis-Plus 是不是不需要写 SQL？不是。它减少通用 CRUD，但业务约束、锁和复杂查询仍要明确设计。参数用绑定方式，不能将用户输入直接拼成 SQL；动态列名和排序字段也要后端白名单。

### 39｜你建了哪些索引？为什么这样设计？

参考回答：cp_document 有联合索引 (org_tag, category, status, group_name)，匹配按组织、类别、就绪状态和分组限定资料的查询；cp_chunk 有 (document_id, chunk_no)，用于按文档获取或清理切片；Outbox 有 (status, next_attempt_at) 和 (status, lease_until)，服务待发送及过期任务扫描。刷题会话和运行记录各有 username 索引。

查询应结合 EXPLAIN 看实际访问方式和扫描量，不能仅看 WHERE 条件写法就说一定走索引。多建索引会增加写入和空间成本；Outbox 的 OR 与排序条件也值得在数据增长后单独看执行计划。

常见追问：联合索引最左前缀、覆盖索引、回表是什么？索引按定义顺序组织；查询利用前导列通常更直接。若所需字段都在索引中，可以减少回表；查询 LONGTEXT 正文一般仍需读取数据行。当前 idx_chunk_document 不是唯一索引，切片唯一性来自 id 主键。

### 40｜SELECT FOR UPDATE 锁住什么？为什么不能只用 synchronized？

参考回答：刷题通过主键查询 cp_practice_session 的会话行，并在事务内加排他锁。对同一行申请不兼容锁的事务需要等待；事务提交或回滚后释放锁。普通 MVCC 一致性读不等同于也必须等待该行锁。[MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

跨应用实例协调依靠数据库锁，而 synchronized 只保护特定 JVM 内的对象。当前从数据库反序列化得到的会话状态对象也可能各不相同，因此同步代码块不能取代数据库锁。

常见追问：有 FOR UPDATE 就一定安全？还要在有效事务内执行，并把读取、检查与对应写入放在同一短事务。查询范围、索引和隔离级别影响锁范围，不能把所有 FOR UPDATE 都描述为只锁一行。

### 41｜项目哪些地方用事务？@Transactional 会失效吗？

参考回答：文档受理用声明式事务，保证文档与 Outbox 一起提交。刷题评测用 TransactionTemplate 分成登记占用和保存结果两个短事务。文件写入、RabbitMQ 投递、ES 写入和模型调用不自动参与 MySQL 的本地事务。

声明式事务通常依赖 Spring 代理，默认代理模式下同类内部自调用不会经过代理，因此可能不生效；默认回滚规则主要针对 RuntimeException 和 Error，受检异常需要按需求配置。捕获异常而不继续抛出或标记回滚，也可能提交。[Spring 声明式事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

常见追问：为什么不把整个上传到 READY 包在一个事务？解析、模型和 ES 太慢，长事务会长期占用连接、锁和数据库资源，而且不能靠 MySQL 回滚外部系统。应分阶段提交，配合状态、幂等和补偿。

### 42｜DeepSeek 评测怎么移到事务外，同时避免并发评测？

参考回答：当前采用“短事务预占 → 事务外模型调用 → 短事务完成”。第一段锁会话行，校验归属、当前题和 requestId，持久化 pending，里面包含答案、questionId、requestId、随机 token 和开始时间，然后提交释放锁。

事务外执行模型评测，必要时生成下一题。第二段重新锁会话行，确认 pending token 与题目仍匹配，再一次保存成绩、完成数量、掌握度、下一题和幂等结果，并清除 pending。

常见追问：A 等待模型时 B 来了怎么办？B 可以获得短事务的行锁，但会看到已有 pending，返回 409 处理中，不会同时调用评测模型。当前实现按整个会话限制一个处理中提交，比仅限制同 requestId 更保守。

### 43｜幂等 key 是什么？唯一约束在哪？同 ID 不同答案怎么办？

参考回答：业务 key 是 sessionId:requestId。已完成提交保存在会话 state_json 的 submissions 映射里；处理中请求保存在 pending。重复请求已完成则重放旧结果，处理中则返回冲突提示；同一 requestId 携带不同 questionId 或答案会被拒绝。

必须说明：当前没有独立提交表，也没有数据库层 UNIQUE(session_id, request_id)。并发安全依赖锁住会话行后检查和保存 JSON 状态，不能把它说成已用联合唯一索引实现。

常见追问：浏览器重试怎么沿用 ID？同一次逻辑提交应保留 requestId。当前示例前端每次点击会生成新 UUID，没有完整的失败重试 ID 保留流程；后端仍会通过 pending 和当前题检查保护状态，但不等同于前端已正确实现幂等重放。

### 44｜模型超时、用户重试或评测进程宕机怎么处理？

参考回答：模型评测默认设 30 秒超时；调用失败或结果不能使用时，当前会退化为规则评分，并提示按概念覆盖与回答深度评分、需人工复核。因此不是所有模型超时都会让本次提交失败。其他运行时错误会尝试用短事务释放自己 token 对应的 pending。

如果进程直接退出，catch 不会执行，state_json 中的 pending 可能持续保留。虽然记录 startedAt，当前没有完整的超时接管和后台恢复机制，不能说已经自动恢复。

常见追问：怎么完善？可拆出评测任务／提交表，使用唯一键、状态、租约和 token，增加扫描恢复与最终写入条件。若模型平台没有幂等请求能力，无法在所有网络不确定场景保证外部模型只调用一次；更可控的是不重复保存业务结果。

### 45｜按分组刷题怎么实现？分组是权限吗？

参考回答：分组用于选择题源。开始刷题传 orgTag、category、groupName，MySQL 查询该范围下 READY 文档 ID，再限制检索和采样；会话记录该分组，错题复练沿用原分组。没有 READY 文档会阻止出题。

权限主要由角色与组织标签决定。groupName 是资料组织维度，不能代替授权。默认问答按组织与类别检索，Agent 请求中的 groupName 主要服务刷题分支，当前不能说所有问答都会按所选刷题组过滤。

常见追问：移动分组为什么不用重算向量？向量取决于正文，group_name 当前在 MySQL 文档记录里，查询时动态转为 documentId 集合过滤；单纯移动分组不改变正文或 embedding。

### 46｜MySQL 与 ES 为什么都保存？文档变更如何处理一致性？

参考回答：MySQL 保存业务状态、切片文本和学习记录，便于事务和恢复；ES 面向全文与向量检索。两者职责不同，不用 ES 保存事务性成绩，也不依赖 MySQL 的简单文本过滤替代混合检索。

当前入库通过任务处理、重建和状态控制协调，仍存在部分写入和跨系统发布窗口。修改正文通常需要重新解析、切块和向量化；只移动分组可更新 MySQL。不能说现有代码已具有完整 CDC、通用版本发布、删除传播与全量一致性校验。

常见追问：怎样进一步做文档更新？让修改意图也进入 Outbox，建立版本与 activeVersion，待新版本完整可用再切换，旧版本延迟清理。删除也应明确文件、元数据、切片和 ES 的任务顺序、重试及授权，而不只执行一条 SQL。

## 第六组：Redis 会话、限流与一致性

### 47｜Redis 和 MySQL 都存会话，分别保存什么？

参考回答：Redis 保存知识问答的短期历史消息，供下一轮 Prompt 理解上下文；MySQL 的 cp_practice_session 保存刷题状态、成绩、答案提交与评测结果，cp_agent_run 保存 Agent 运行结果。MySQL 没有一个完整对应所有普通问答消息的历史归档表，不能说两边是同一份聊天记录的缓存和持久层。

Redis 会话 key 包含已校验的用户、组织和会话标识；当前以 JSON 字符串保存消息列表，写入后 TTL 为 6 小时。读取用于 Prompt 时取最近六条消息，不是六轮对话，也不代表 Redis 只存六条。

常见追问：Redis 清空会丢成绩吗？MySQL 中已保存的刷题成绩仍在，但短期问答上下文可能丢失，不能承诺从 MySQL 自动还原全部聊天历史。

### 48｜并发追加聊天历史安全吗？过长怎么办？

参考回答：当前 Redis 追加采用 GET → 反序列化 → 添加消息 → SET，并不是一个原子操作。两个请求读到同一旧列表后各自写回，可能覆盖对方消息。ConcurrentHashMap 也不能解决远端 Redis 的读改写竞争。

进一步可改用 Redis List，通过 Lua 把 RPUSH、LTRIM 和 EXPIRE 组合成原子更新，或采用 WATCH 乐观重试，并为消息加 ID、序号。需要同时设保存条数或长度上限，而不是只在构建 Prompt 时截取最后六条。

常见追问：这已经用了 Lua 吗？没有，当前简历不要写。还要考虑同一会话并发生成时消息顺序与用户／助手配对，单纯原子追加不能自动解决业务顺序问题。

### 49｜Redis 限流怎么做？为什么 INCR 后 EXPIRE 有风险？

参考回答：知识问答当前按组织标签计数，key 类似 codeprep:rate:knowledge:java。每次 INCR，第一次计数时设置一分钟过期，超过 60 拒绝。这是以首次请求建立窗口的简单固定窗口计数，不是令牌桶或滑动窗口。当前没有统一覆盖所有 Agent、上传和刷题入口。

INCR 与 EXPIRE 是两次操作，如果中间故障，计数 key 可能缺失过期时间。可以用 Lua 在一次原子执行里完成计数和首次数设置 TTL。[Redis INCR 限流示例](https://redis.io/docs/latest/commands/incr/)

常见追问：Redis 不可用时怎么办？当前限流失败放行，聊天尝试本地内存兜底。这样偏向可用性，但模型费用保护减弱，且各实例本地状态不一致；生产方案需要明确降级策略和告警，不能说当前是强限流。

### 50｜缓存穿透、击穿、雪崩与你的项目有什么关系？

参考回答：穿透是重复查询不存在的数据，可用输入校验、短期空值缓存等应对；击穿是热点 key 失效导致大量请求同时重建，可用互斥或 single-flight 合并；雪崩是大量 key 同时失效或缓存故障，可用过期时间打散、限流和分级降级。

但本项目当前主要使用 Redis 做会话和限流，没有完整的检索结果缓存实现。不能因为配置存在 cache-seconds，就说已实现热点 RAG 缓存、布隆过滤器或缓存一致性方案。

常见追问：如果加检索缓存，key 怎么设计？至少包括查询、组织／权限范围、类别、分组或文档集合、索引版本以及必要模型版本；不能只用问题文本，否则可能跨组织复用结果。文档更新后按版本切换或精准失效。

## 第七组：登录、权限、SSE 与 WebSocket

### 51｜用户如何登录？后续请求如何识别身份？

参考回答：前端向 /api/auth/login 提交用户名和密码，服务读取账号信息并用 BCrypt 校验摘要。成功后签发 JWT，包含用户名、角色和组织标签，默认有效期 12 小时。之后 HTTP 请求通过 Authorization: Bearer token 携带。

JWT 过滤器验证签名和有效性，从 token 取用户名，再读取账号生成当前权限，放入 SecurityContext。项目使用无状态安全会话，不依赖服务端 HttpSession 保存登录态。密码不能用可逆加密或明文比较代替 BCrypt 的匹配逻辑。

常见追问：JWT 内容能不能被客户端看到？能，签名不是加密，不应在载荷中放密钥。JWT 声明了角色，但当前 HTTP 请求的实际权限还会从账号数据重新加载；不要说角色更新只能等 JWT 过期。

### 52｜角色和组织标签怎样控制访问？能直接改 orgTag 越权吗？

参考回答：角色决定能力，组织标签决定数据范围。当前 OWNER 有管理旁路；其他用户访问知识域需要对应组织标签及读／写权限，EDITOR 可具备写权限。权限检查后，检索还必须带组织条件，防止把不同知识域片段拼到同一个 Prompt。

会话 ID 还绑定 username:orgTag，别人提交另一个用户的会话 ID 会被拒绝；刷题记录也校验 username 归属。上传和分组变更不能只检查前端按钮是否可见。

常见追问：是所有文档都只属于上传者本人吗？当前主要是组织标签隔离，cp_document 没有独立的上传者 ACL 字段；同组织授权用户可共享资料。不能把“私有知识库”说成严格每用户独占。

### 53｜JWT、Redis 会话、WebSocket 鉴权分别是什么关系？

参考回答：JWT 用于认证身份；Redis 的会话数据是模型上下文，Redis key 存在并不等于用户已登录。HTTP 经过 JWT 过滤器，WebSocket 由握手拦截器验证 token 并保存 Authentication，收到消息后仍检查组织权限。

当前浏览器在 WebSocket URL 查询参数中传 token，握手成功后用连接属性读取身份。它满足本地演示，但正式部署要使用 TLS/WSS 并避免 token 出现在访问日志；可设计短期连接票据。当前不是已实现完整刷新 token、撤销黑名单和长连接持续重新授权的方案。

常见追问：握手放行 /ws/** 是否等于不鉴权？不是，实际鉴权在握手拦截器。但长连接中的 token 过期和权限变化仍需单独设计，HTTP 每次鉴权不能自动覆盖整个连接生命周期。

### 54｜你到底用了 SSE 还是 WebSocket？为什么简历两处不一样？

参考回答：需要分三段说。后端请求 DeepSeek 的 stream API，使用 WebClient 读取 SSE 增量；知识问答页面连接 /ws/agent，发送 KNOWLEDGE_ASK，后端把增量封装为 WebSocket 消息逐段推送；后端还提供 /api/knowledge/chat/stream 的 SSE 接口。当前 Agent 工作台主要通过 HTTP /api/agent/runs 获取完整结果。

SSE 是基于 HTTP 的服务端向客户端事件流，适合单向答案推送；WebSocket 支持连接中的双向消息，适合交互命令和实时事件。流式只说明增量返回，不代表首个字没有检索、审核的等待，也不保证每个事件严格对应一个 Token。

常见追问：简历怎么统一？正文写“通过 WebSocket 推送模型增量回答”，技术栈写 WebSocket；想保留 SSE，可写“WebSocket／SSE”，并准备说明上游与下游的区别。不能说前端正在使用 SSE，也不能说 Agent 全程都是 token 流。

### 55｜流式回答中断怎么办？现在有没有重连、取消和断点续传？

参考回答：当前事件包括 session、retrieval、delta、done 和 error，前端拼接 delta，收到 done 后结束连接；正常流完成后后端保存本轮上下文。错误路径会发送错误提示，但没有完整的序号、事件重放或答案断点恢复协议。

进一步需要 requestId 与事件序号、完成状态、客户端取消与服务端订阅取消绑定，以及断线后查询最终结果或按游标恢复。当前不能保证浏览器关掉后所有上游模型请求都立即取消，也不能把不完整答案当成完成结果存档。

常见追问：为什么连接好了还是没字？现在先完成检索和证据审核才进入生成，流式方法前置步骤包含同步等待，首个业务事件也可能较晚。需要分别测连接、检索、审核、首字和总耗时，不能只说 WebSocket 已连接就代表模型正在输出。

## 第八组：Java 后端追问、测试与简历表达

### 56｜用了 WebClient 和 Flux，项目就是全链路响应式吗？

参考回答：不是。项目以 Spring MVC 为主，同时引入 WebFlux 组件使用 WebClient 和 Flux 消费模型流。多个检索、审核或模型方法仍调用 block，数据库使用阻塞式 MyBatis-Plus，不能描述为端到端非阻塞架构。

Flux 用来表达一串增量事件，但如果进入流之前就同步等待检索和审核，仍会占用调用线程。优化要明确阻塞工作运行在哪个线程池，设置有界队列、并发限制、超时和取消，而不是只把返回类型改成 Flux。

常见追问：线程池越大吞吐越高吗？取决于 CPU、数据库连接数、模型额度和 ES 容量；盲目加线程会增加排队、内存及超时。项目还需按实际负载测量，不能声称已做高并发压测。

### 57｜项目最容易关联哪些 Java 基础题？怎样结合业务回答？

参考回答：第一是集合和并发：ConcurrentHashMap 的单次安全操作不代表 get→判断→put 的复合逻辑原子，分布式占用还要靠数据库。第二是资源管理：解析文件用 try-with-resources 关闭流，心跳线程在 finally 停止。第三是异常处理：区分可重试故障、永久输入错误和业务冲突，不把所有异常吞掉后返回空列表。

第四是 UUID 与业务标识：documentId 标识文档，chunkId 标识切片，requestId 标识一次逻辑提交，worker token 标识某次处理资格；它们用途不同。第五是事务代理与线程边界：异步线程不会自动继承调用线程事务，内部方法调用也不自动经过事务代理。

常见追问：线程安全的 Map 里面放 ArrayList 就安全了吗？不是。Map 保护映射操作，列表内容和多个字段的联合更新仍要同步或设计不可变快照。当前 Redis 本地降级与上传内存状态不应被描述为完善的多实例方案。

### 58｜你怎么验证这些可靠性机制真的有效？

参考回答：按失败窗口设计用例：文档与 Outbox 同提交或同回滚；发送 NACK／returned／超时后任务保留；两个消费者争抢只有一个领取；READY 重复投递不重做；处理中租约过期可补发；评测并发时一个请求调用模型、另一个得到处理中；模型等待期间不持有事务；证据弱、超时、虚构 ID 时不生成答案。

最近一次记录为 77 个用例，实际执行 75 个通过，2 个显式实服务测试默认跳过。数据库自动化部分使用 H2，并配合 mock／本地服务桩覆盖业务流程；这不等同于 75 个真实 MySQL、RabbitMQ、ES 集成测试，也不是生产容灾证明。

常见追问：还应该怎么测？在独立测试数据上做真实 MySQL 并发、kill 进程、MQ 断连、ES 部分失败和模型慢响应演练，记录恢复时间、重复副作用及数据一致性。本轮整理没有重新跑这些演练。

### 59｜有哪些真实结果可以写？Docker 如何使用？

参考回答：已有一份自建 Markdown 资料通过真实上传链路得到 29 个 READY 切片，测试包含 60 个可回答问题和 8 个库外问题。在该小规模自标注集合里，原混合检索 Recall@8 为 100%，Precision@8 约 13.54%，8 个库外问题都返回了候选。这暴露出证据不足判断缺失，而不是可以宣传为“问答准确率 100%”。

本机单次上传 HTTP 约 31 毫秒、观察到 READY 约 33 秒，只对应这份自建 Markdown 和当时环境，不能写成 100 页 PDF 或生产性能。新增审核的完整质量复测未完成，遇到超时及 HTTP 503，没有可发布的新全量提升指标。

Docker Compose 用于本地 MySQL、Redis、RabbitMQ、ES＋IK 环境，MySQL、RabbitMQ 和 ES 配有数据卷；后端、前端与模型服务并非全部在这个 Compose 内。不能称为完整云原生生产集群。

常见追问：这组样本能证明泛化吗？不能，语料小且问题与资料自建自标注，应增加独立问题、真实复杂 PDF、文档更新及跨组织样本，并分别统计质量、故障和延迟。

### 60｜这份简历哪些说法值得调整，怎样回答“还有什么不足”？

参考回答：技术点整体能对应项目，但表述要和实现保持一致：流式通信建议统一 WebSocket／SSE；RRF 写“基于 RRF 的融合排序”；按结构切块可以保留，但不写精确 Token 切分、语义聚类或 PDF 页码定位；分片上传可以保留，但不承诺跨重启完整续传；MySQL 幂等应讲行锁和状态快照，不能说已建独立提交唯一索引。

对不足可以选两项讲透：第一，当前文档租约控制之外，还需要版本化索引和写入隔离来完善极端接管场景；第二，刷题 pending 缺少宕机恢复。然后说明为什么要改、具体怎么做及如何验证，不要只泛泛说“以后提高性能”。

可替换的简历表述：

> 构建异步知识库入库链路：使用 Tika 解析与结构切块，通过 MySQL Outbox 和 RabbitMQ 调度向量化、ES 建索引；结合条件更新、租约与失败重试管理文档处理状态。
>
> 实现混合 RAG 问答：结合 IK/BM25 与 2048 维 KNN 召回，采用基于 RRF 的融合排序，并增加证据充分性审核与片段选择；依据引用资料生成回答，区分证据不足与服务故障。
>
> 基于 MyBatis-Plus 持久化文档和学习状态，通过短事务预占、事务外评测及 requestId 结果重放处理重复提交；使用 Redis 保存短期上下文并计数限流，通过 WebSocket 推送模型增量回答。

常见追问：能不能说独立设计并实现？只有本人确实承担并理解对应工作时才这样写。可以准确描述自己负责的设计、编码、联调和问题定位范围；项目成果与个人贡献是两件需要分别说明的事。
